# Проверка значений по умолчанию для маршрутов Odyssey

Дата проверки: 2026-09-11

Область проверки: `docs/configuration/rules.md` и соответствующая реализация конфигурации маршрутов в текущей версии Odyssey.

## Итог

Таблица значений по умолчанию в `docs/configuration/rules.md` не полностью соответствует коду. Четыре значения прямо противоречат инициализации:

| Параметр | Указано в документации | Фактическое начальное значение |
|---|---:|---:|
| `server_drop_on_cached_plan_error` | `no` | `yes` |
| `client_show_id` | `no` | `yes` |
| `pool_reset_timeout_ms` | `0` | `1000` мс |
| `pool_reserve_prepared_statement` | `yes (0)` | `yes (1)` |

Кроме того, эффективные значения некоторых параметров пула зависят от режима pooling. Показывать только значения сразу после инициализации недостаточно: перед использованием маршрута валидатор изменяет их.

## Источники фактических значений

При проверке использовались следующие участки кода:

- `sources/rules.c:513-587` — создание маршрута и его начальные значения;
- `sources/pool.c:13-35` — создание пула и его начальные значения;
- `sources/cfg/convert.c:644-820` — применение явно заданных параметров; макросы `COPY_*` заменяют значение только тогда, когда параметр присутствовал в конфигурации;
- `sources/rules.c:1680-1782` — валидация и нормализация режима пула;
- `sources/rules.c:2027-2160` — проверка storage, role и authentication;
- `sources/tsa.c:18-64` — вычисление эффективного `target_session_attrs`;
- `sources/cfg/parse.y:1180-1893` — допустимые значения и числовые диапазоны.

В отчёте различаются:

- начальное значение — присваивается при создании маршрута или пула;
- эффективное значение — получается после чтения конфигурации и валидации;
- не задано — значение отсутствует, хотя при использовании может применяться fallback.

## Значения, зависящие от режима пула

`od_rule_pool_alloc()` создаёт пул со следующими начальными значениями:

```text
pool_discard                    yes
pool_smart_discard              no
pool_reserve_prepared_statement yes
```

Затем `od_pool_validate()` нормализует их:

| Режим пула | `pool_reserve_prepared_statement` | `pool_discard` | `pool_smart_discard` |
|---|---:|---:|---:|
| `session` | `no` | `yes` | `no` |
| `transaction` | `yes` | `no` | `yes` |
| `statement` | `yes` | `no` | `yes` |

В режиме `session` резервирование prepared statements принудительно отключается. В режимах `transaction` и `statement` включённое резервирование prepared statements приводит к замене обычного discard на smart discard.

Это эффективные значения при отсутствии всех трёх параметров в конфигурации. В документации следует привести эту таблицу либо явно обозначить существующие значения как начальные, до валидации.

## Другие несоответствия документации

### Дублирование устаревших LDAP-параметров

`ldap_pool_size`, `ldap_pool_timeout` и `ldap_pool_ttl` дважды присутствуют в сводной таблице. В первом месте они описаны как рабочие настройки, во втором — как deprecated. Фактически парсер только выдаёт предупреждение и игнорирует их значения (`sources/cfg/parse.y:1361-1378`).

Подробные разделы `docs/configuration/rules.md:344-384` также устарели.

### Неверное описание `auth_common_name default`

В таблице сказано, что специальное значение разрешает любой CN сертификата. Реализация вызывает проверку сертификата с `rule->user_name` (`sources/auth.c:778-783`). Верной является формулировка из подробного раздела: проверять CN по текущему пользователю.

### Неверное имя параметра discard query

Подробный раздел называется `pool_discard_string`, но парсер принимает `pool_discard_query` (`sources/cfg/keywords.c:172`). Ссылки на `pool_discard_string` также следует переименовать.

### Неполный список значений `authentication`

Сводная таблица содержит `external`, и валидатор его принимает (`sources/rules.c:2130-2132`), но в подробном списке `docs/configuration/rules.md:89-98` это значение отсутствует. В примечании самой таблицы `external` также пропущен в списке валидируемых значений.

### Неполный список режимов пула

Таблица и валидатор поддерживают `session`, `transaction` и `statement`, но подробный список `docs/configuration/rules.md:407-412` не содержит `statement`.

### Неверное описание `role`

Документация называет допустимыми значениями `admin` и `client`. На самом деле конвертер принимает:

```text
admin
stat
notallow
```

Значение `client` не принимается (`sources/cfg/convert.c:703-715`). Обычный remote-маршрут оставляет `role` незаданным. Для local-маршрута отсутствие роли преобразуется в `stat` при валидации (`sources/rules.c:2066-2083`).

### Неверная семантика override для `log_query`

Документация утверждает, что per-route параметр переопределяет глобальный `log_query`. Фактически логирование включается, если истинно хотя бы одно из значений:

```c
instance->config.log_query || route->rule->log_query
```

Таким образом, per-route `yes` может включить логирование при глобальном `no`, но per-route `no` не может выключить глобально включённое логирование (`sources/frontend.c:1887-1951`).

### Некорректная рекомендация для `pool_notice_after_waiting_ms`

Начальное значение равно `-1`, что отключает уведомления. Однако парсер запрещает явно задавать отрицательные значения (`sources/cfg/parse.y:1570-1582`). Формулировка «Negative values disables the feature» создаёт впечатление, что отрицательное значение можно указать в конфигурации. На практике для отключения параметр нужно не задавать.

### Параметры, отсутствующие в сводной таблице

В таблице отсутствует ряд документированных или принимаемых парсером route-настроек:

- `auth_query_db`, `auth_query_user`;
- `pool_notice_after_waiting_ms` — начальное значение `-1`;
- `pool_attach_check` — default `yes`;
- `pool_acquire_fail_fast` — default `no`;
- `shared_pool`;
- `options`, `backend_startup_options`;
- `group_query`, `group_query_user`, `group_query_db`;
- `watchdog_lag_query`, `watchdog_lag_interval`;
- `keepalive`, `keepalive_keep_interval`, `keepalive_probes`, `keepalive_usr_timeout`.

Две последние группы принимаются route-парсером, но не имеют отдельных описаний в `rules.md`.

## Рекомендуемые исправления

1. Исправить четыре прямо неверных значения по умолчанию.
2. Описать эффективные defaults пула отдельно для каждого режима pooling.
3. Удалить рабочие описания deprecated-параметров LDAP, оставив только уведомления об их игнорировании.
4. Разделить незаданное и эффективное значения для `client_max`, `target_session_attrs`, `pool_routing` и `role`.
5. Переименовать `pool_discard_string` в `pool_discard_query`.
6. Исправить описания `auth_common_name default`, `role`, `log_query` и `pool_notice_after_waiting_ms`.
7. Добавить пропущенные route-параметры в сводную таблицу и описать route-level параметры keepalive и watchdog.

## Вывод

Большинство простых нулевых и незаданных значений в таблице совпадают с кодом. Однако сейчас таблицу нельзя считать достоверным справочником эффективных runtime-defaults. Наиболее существенные расхождения: включённые по умолчанию `server_drop_on_cached_plan_error` и `client_show_id`, timeout сброса соединения в одну секунду и изменение discard-поведения валидатором при включённой поддержке prepared statements.
